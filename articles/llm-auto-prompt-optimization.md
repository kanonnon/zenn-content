## はじめに

こんにちは！株式会社SCIENの機械学習エンジニアの雨宮です。

突然ですが、プロンプトエンジニアリングにどれくらい時間を使っていますか？

LLM を使った機能を作っていると、だいたいこうなると思います。

1. プロンプトを書いて、データで試す
2. 出力を眺めて「あー、ここ間違えてる」と気づく
3. 「〇〇の場合は必ず△△としてください」と一文足す
4. 今度は別のところが壊れる
5. 1 に戻る

気づけば「必ず」「絶対に」が並んだ呪文のようなプロンプトができあがり、しかもモデルを乗り換えるとまた効かなくなる。正直、めんどくさいですよね。

でもよく考えると、この作業は「間違えた例を見て、原因を考えて、文章を直す」の繰り返しです。それって、LLM がいちばん得意なことでは？

というわけで本記事では、**プロンプトエンジニアリングを LLM 自身にやらせる仕組み**を作った話をします。

## なぜ作ったのか

LLM を様々なタスクに使っていると、タスクやモデルが変わるたびにプロンプトエンジニアリングをやり直すことになり、その出来は担当者の根気と勘に左右されがちです。

一方で、このループには見覚えがあります。「データで試す → 間違いを見る → 直す」は、ニューラルネットの学習ループと同じ構造をしています。

| ニューラルネットの学習 | プロンプトエンジニアリング |
|---|---|
| 重み | プロンプト |
| 損失 | 間違えた問題 |
| 勾配 | 「なぜ間違えたか」の分析 |
| 重みの更新 | プロンプトの書き直し |

違うのは、勾配にあたる「なぜ間違えたか」を人間が考えている点だけです。であれば、それも LLM に書かせればいい。

そこで作ったのが、自動プロンプト最適化基盤です。この基盤を使う人が用意するのは、次の2つだけです。

- 入力データとそれに対する正解データ
- 評価指標

あとは実行するだけで、LLM がプロンプトの生成・評価・誤答分析・書き直しを繰り返し、最後に最も良かったプロンプトを出力します。

## 仕組み：LLM に解かせて、LLM に直させる

やっていることをひとことで言うと、**LLM にタスクを解かせ、間違えたらその答案を LLM に見せてプロンプトを直させる、をひたすら繰り返す**だけです。本記事では前者を **タスク LLM**、後者を **オプティマイザ LLM** と呼びます。同じモデルが両方を兼ねても構いません。

流れは、叩き台を作る初期化（1）と、「ミニバッチを解く → 新しい候補を作る → 評価して選ぶ」を1ステップとして回す改善ループ（2〜4）に分かれます。個々の部品は既存の研究がベースとなっているので、対応する論文は各項目で挙げています。

![](/images/apo-cord/flow-7abfdbe0.png)
*仕組みの全体像。丸数字は以下の見出しの番号、色は処理の担当（タスク LLM / オプティマイザ LLM / コードのみ）を表す。*

### 1. 叩き台を作らせる

**training set の正解例から指示文を逆算させて初期候補を作り、有望なものを改善ループの出発点（ビーム）にします**（APE[^ape]）。オプティマイザ LLM に入出力のペアを見せ、次のような穴埋め形式で、その出力を生んだ指示を推測させます。

> 私は友人にあるタスクを指示しました。友人は私の指示を読み、以下の各入力に対して出力を書きました。（中略）空欄を埋めてください: 私の指示は「<空欄>」でした。

見せるペアを変えながら候補を量産し、validation set の一部で評価して上位を残す、という絞り込みをサンプル数を増やしながら繰り返します。

### 2. ミニバッチを解かせて、誤答を集める

**ビームの各プロンプトで、training set から取ったミニバッチを解かせ、満点でなかった出力を誤答として集めます。** 集めた誤答が、次の 3 で新しい候補を作る材料になります。ミニバッチには、過去のステップで繰り返し誤答しているサンプルを優先的に入れ、これまでの修正で解けていない問題に改善を集中させます。

### 3. 誤答から新しい候補を作る

**集めた誤答をもとに、「指示文の書き直し」と「few-shot 例の入れ替え」の2通りで新しい候補を作ります。**

#### 指示文の書き直し

誤答（入力・モデルの出力・正解）をオプティマイザ LLM に渡してプロンプトの問題点を挙げさせ、挙がった問題点ごとに書き直させます（ProTeGi[^protegi]）。書き直した候補には、言い換えのバリエーションも加えます。ニューラルネットの学習でいえば、ダメ出しが勾配の計算、書き直しがパラメータの更新にあたります。

ただし、今のプロンプトと今回の誤答だけを見せると、過去に効かなかった修正を何度も提案しがちです。そこで依頼文には、これまでに評価したプロンプトと、その validation set でのスコアの一覧を含め、低スコアの候補と同じ方向の変更を避けるよう指示します（OPRO[^opro]）。繰り返し誤答しているサンプルについては、過去の修正では解けなかった問題であることも明示します。

#### few-shot 例の入れ替え

例えば出力形式など、指示文で説明するより実例で示したほうが確実に伝わる情報もあります。そこで候補を「指示文 + few-shot 例」の組として扱い、few-shot 例も最適化の対象にします（MIPROv2[^mipro]）。

![](/images/apo-cord/fewshot-0869f9d1.png)
*few-shot 例の扱い。上：推論時は、候補が持つ ID から training set の画像と正解 JSON を取り出して並べる。下：新しい候補は ID の追加・入れ替え・削除で作る。*

few-shot 例は training set のサンプル ID として持ち、推論時にデータセットの正解を差し込みます。LLM に例を書かせないので、誤った正解が混入することはありません。新しい候補は、2 で集めた誤答を例に追加する・今の例と入れ替える・例を削除する、という ID の操作だけで作れるため、LLM の呼び出しも不要です。

### 4. 評価して、ビームに残す候補を選ぶ

**今のビームと新しい候補をまとめて validation set で評価し、次のステップのビームに残すプロンプトを選びます。** すべての候補を validation set 全件で評価するとコストが大きいため、候補選びを多腕バンディット問題とみなし、UCB アルゴリズムで有望な候補に評価を寄せながら上位を選びます。少数サンプルでの推定値は上位ほど過大評価されやすいため、上位の候補は validation set 全件で評価し直してからベストを判定します。few-shot 例を入れ替えた候補も書き直しの候補と同じように選抜されるので、few-shot 例が効かないタスクでは自然に採用されません。

validation set でのベストスコアが更新されなくなるまで 2〜4 を繰り返し、最後に validation set でベストスコアだったプロンプトを test set で評価します。

## 実験：レシート画像から構造化データを抽出するタスクで試す

### 設定

今回用いたデータセットは CORD-v2[^cord] で、レシート画像から品名・数量・金額などの構造化データを抽出し、JSON で出力するタスクです。評価指標には、出力の JSON を `total.total_price = 20,000` のような「キーの経路と値」のペアに分解し、正解のペアとの F1 をとったものを使いました。

LLM には Qwen3-VL-8B-Instruct を使い、タスク LLM とオプティマイザ LLM の両方をこのモデルに担当させました。つまり、同じモデルが自分用のプロンプトを自分で直す構成です。

### 結果

改善ループ（LLM 呼び出し約9,400回）を回した結果、最終的なプロンプトは test set で F1 0.76 となりました。validation set でのスコアの推移は次のとおりです。

![](/images/apo-cord/val_curve-009e3fad.png)
*改善ステップごとの、validation set でのベストスコア。*

**叩き台の時点で、キー名はある程度当てていました。** 正解例から指示文を逆算させただけで、`total_price` や `cashprice` といったスキーマ固有のキー名まで拾えています。ただし、validation set でのスコアは 0.33 にとどまっていました。

**step 1 で few-shot 例が入り、0.66 まで伸びました。** その時点の誤答から3件が、そのまま few-shot 例として採用されています。出力形式を伝えるうえで、正解の JSON を丸ごと見せる効果は大きいようです。

**step 2 では、ダメ出しを受けてスキーマを具体的に書き足した候補がトップになりました。** 実際のダメ出しと書き直しがこちらです。

![](/images/apo-cord/rewrite-85a816c0.png)
*ダメ出しと書き直しの例。*

オプティマイザ LLM はスキーマの説明不足を原因として挙げ、キー名に加えて「品目が1つならオブジェクトにする」「カンマ区切りを残す」といったルールを書き足しています。

以降は「`1X` のような数量表記は `cnt` に入れる」といった細かいルールが加わりながら 0.8 前後まで伸び、更新が止まったところで early stopping しました。

### 1枚のレシートで見ると

叩き台と最終プロンプトで、同じレシートに対する出力を比べます。

![](/images/apo-cord/eval_pairs-c7c88af0.png)
*validation set のレシート1枚での評価*

叩き台の出力は、`total_price` などのキー名は合っているものの、品目が1つでも配列で出力し、金額はカンマを落として `20000` としています。キーの経路か値のどちらかがずれているため一致するペアはなく、F1 は 0 です。読み取り自体はできていて、出力形式で失点している例といえます。最終プロンプトでは、正解と完全に一致しました。

## やってみて分かったこと

### できあがるプロンプトは、人間には読みにくい

最終的なプロンプトは791字まで膨らみ、次のような文も含まれていました。

> レシートに「1.00xITEMs」や「@9000」などの記号が含まれる場合は、それらをそのまま「cnt」または「unitprice」の値として反映し、他のフィールドに埋め込まないよう**厳密に指示してください**。

「指示してください」はオプティマイザ LLM への依頼文の口調が紛れ込んだもので、タスク LLM への指示としては意味をなしていません。途中の候補には「レシpte」という崩れた表記も現れました（最終版では直っています）。冒頭で書いた「呪文のようなプロンプト」を LLM も書いてしまうのは、ちょっと面白いところです。スコアは出ていても保守しやすい文章ではないので、採用前には一度読んで整えるのがおすすめです。

:::details 最終的なプロンプト

> レシート画像の内容を、CORDスキーマ準拠のJSON形式で抽出してください。
>
> メニュー項目は「menu」キーに配列として記載し、各項目には「nm」（品名）、「cnt」（数量）、「price」（合計金額）を必ず含めます。
>
> 「unitprice」（単価）は、レシートに「@」または「1X」などの特殊記号が使用されている場合に限り、その記号を含めて「unitprice」フィールドに明示的に記載してください。
>
> それ以外の場合は単価を省略し、「price」フィールドに合計金額のみを記載してください。
>
> メニューが1項目のみの場合は「menu」をオブジェクトとして記述します。
>
> 「sub_total」には小計（subtotal_price）、サービス料（service_price）、税金（tax_price）、割引（discount_price）を必ず含み、「total」には合計金額（total_price）を必ず含み、支払い方法がカードの場合は「creditcardprice」、現金の場合は「cashprice」、お釣りがある場合は「changeprice」を必ず含めます。
>
> レシートに「1.00xITEMs」や「@9000」などの記号が含まれる場合は、それらをそのまま「cnt」または「unitprice」の値として反映し、他のフィールドに埋め込まないよう厳密に指示してください。
>
> ただし、「menuqty_cnt」などの記号は「cnt」フィールドに明示的に配置し、レシートに記載された位置情報に基づいて、その内容を「menu」の各項目の「cnt」に直接反映するように指示してください。
>
> すべてのフィールドはレシートに印字された内容を忠実に反映してください。
>
> 特に、「1x」などの数量記号は「cnt」フィールドに明示的に配置し、「unitprice」フィールドには単価として反映しないでください。

:::

### 評価の設計は、人間の仕事として残る

オプティマイザ LLM は、与えられた評価指標に対して素直に最適化します。裏を返すと、評価指標が本当に測りたいものからずれていれば、プロンプトもそのずれた方向に最適化されます。

今回の CORD は、正解の JSON が用意されていて、評価指標も「キーと値のペアの F1」で機械的に決められる、恵まれたタスクでした。たとえば今回の評価指標では `20,000` と `20000` を別物として扱ったので、LLM は「カンマを残す」というルールを覚えました。これが望ましい振る舞いかどうかは、本来はタスクの目的しだいです。

実務では、こうした判断を一つひとつ人間が決める必要があります。

- そもそも正解データがなく、アノテーションの基準づくりから始まる
- 表記ゆれや部分一致をどこまで正解とみなすかを決める
- 誤りの重さは項目ごとに違う（合計金額の誤りは致命的でも、品名の一文字違いは許容できる、など）
- 人によって正解の判断が割れるケースをどう扱うかを決める

ここを曖昧にしたまま最適化を回すと、「評価指標上は高いのに、現場では使えないプロンプト」ができあがります。プロンプトを書く手間を LLM に任せられる分、人間は「何を正解とし、どう評価するか」の設計に時間を使うべき、というのが今回の実感です。

評価設計の大切さは、物体検出を題材にした弊社の以前の記事でも紹介しているので、あわせてご覧ください。

## 終わりに

ここまでお読みいただきありがとうございました！

本記事では、LLM にタスクを解かせ、その誤答をもとに LLM 自身にプロンプトを直させる仕組みと、レシート画像から JSON を抽出するタスクでの実験結果を紹介しました。ポイントは次の3点です。

- 誤答の分析に基づく指示文の書き直しと few-shot 例の入れ替えを繰り返すことで、test set で F1 0.76 のプロンプトが得られた
- 改善の中心は、キーの構造や値の書式といった出力形式の取り決めを、LLM が誤答から見つけて書き足していく過程だった
- 一方で、できあがるプロンプトはそのままでは保守しにくく、何を正解とし、どう評価するかの設計は人間の仕事として残る

プロンプトを書いては直す試行錯誤の多くは、LLM に任せられます。そのぶん人間は、評価指標とデータの設計に時間を使えるようになります。
